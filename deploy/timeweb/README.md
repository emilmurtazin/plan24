# Развёртывание Plan 24 на Timeweb Cloud — собственный сервер

> Есть второй вариант — **через App Platform** (без своего сервера, домен и TLS даёт платформа): см. `APPS.md`. Этот документ — про облачный сервер с Docker.

Схема: **интернет → Caddy (80/443, TLS) → web (2 процесса) → управляемый PostgreSQL по приватной сети.**
Рядом в том же compose — `scheduler` (утренние задания и вечерние напоминания) и, при необходимости, `tg-poll` (бот в режиме опроса).
Наружу открыты только 22 (SSH), 80 и 443; порт БД наружу не публикуется.

> Сведения о Timeweb — по их документации на 7 октября 2026 (timeweb.cloud/docs). Тарифы, названия пунктов панели и набор привилегий
> могут измениться — перед стартом сверьтесь с панелью. Что в этой инструкции проверено, а что нет, — в конце.

## 0. Решения до начала
| Вопрос | Рекомендация |
|---|---|
| Регион | Москва или Санкт-Петербург: персональные данные граждан РФ должны храниться в РФ (152-ФЗ). Сервер и БД — в одном регионе и **в одной частной сети (VPC)**. |
| База | Управляемый PostgreSQL **16** (проверялось на 16; приложение требует 14+). По документации Timeweb, на минимальной конфигурации кластера нельзя создавать дополнительных пользователей — берите тариф выше. |
| Сервер | Ubuntu 24.04, от 2 vCPU / 4 ГБ: web (2 процесса) + scheduler + Caddy. Это оценка, а не замер — после запуска посмотрите `docker stats`. |
| Домен | Любой, A-запись на публичный IP сервера (нужна до первого запуска Caddy — он выпускает сертификат Let's Encrypt). |
| Почта | Любой SMTP-сервис. Для доставляемости на домене отправителя настройте SPF, DKIM, DMARC. |
| Telegram | **Сначала прочитайте раздел «Telegram с российских серверов».** |

## 1. База данных (панель Timeweb → Базы данных → PostgreSQL)
1. Создайте кластер PostgreSQL 16 в нужном регионе, подключите к частной сети, **включите автоматические резервные копии**.
2. Запишите: приватный IP кластера, имя базы, пользователя кластера (в Timeweb — `gen_user`) и его пароль.
3. Приложению в этой инструкции **не** даётся пользователь `gen_user`: он владелец БД и обходит защиту строк. Для приложения создаётся отдельная роль (шаг 4).

## 2. Облачный сервер
Создайте сервер Ubuntu 24.04 в той же частной сети, добавьте SSH-ключ, запишите публичный IP, создайте DNS-запись.

## 3. Предполётная проверка базы (с сервера или с вашего компьютера, если разрешён доступ)
```bash
psql "postgresql://gen_user:ПАРОЛЬ@ПРИВАТНЫЙ_IP:5432/ИМЯ_БД?sslmode=require" -f deploy/timeweb/db-preflight.sql
```
Скрипт печатает таблицу «проверка | значение | вердикт». Нужно: версия 14+, `может создавать роли — ОК`, `может создавать таблицы в public — ОК`.
Если там «НЕТ» — **остановитесь** и устраните (чаще всего: не выдана привилегия CREATE_ROLE пользователю кластера → выдайте её в панели, раздел «Пользователи и привилегии»).
Пришлите мне вывод этого скрипта, если что-то непонятно, — отвечу, что менять.

## 4. Роль приложения
```bash
psql "postgresql://gen_user:ПАРОЛЬ@ПРИВАТНЫЙ_IP:5432/ИМЯ_БД?sslmode=require" -v ON_ERROR_STOP=1 \
     -v app_pw='ПРИДУМАННЫЙ_ПАРОЛЬ_ПРИЛОЖЕНИЯ' -f deploy/postgres/init-roles-managed.sql
```
Создаётся `plan24_app` (не суперпользователь, **без** обхода RLS, не владелец таблиц). Скрипт можно запускать повторно (меняет пароль).

## 5. Подготовка сервера
```bash
scp -r deploy root@IP:/root/ && ssh root@IP "ADMIN_IP=ВАШ_IP sh /root/deploy/timeweb/bootstrap.sh"
```
Ставит Docker, клиент PostgreSQL, файрвол (22/80/443), fail2ban, автообновления безопасности, создаёт пользователя `plan24`.
Проверьте вход `ssh plan24@IP`, затем отключите вход root и по паролю (`PermitRootLogin no`, `PasswordAuthentication no` в `/etc/ssh/sshd_config`).

## 6. Релиз и настройка
```bash
# на вашем компьютере: упаковать и выложить релиз (каталоги backend, frontend, deploy)
tar czf plan24.tgz backend frontend deploy && scp plan24.tgz plan24@IP:/opt/plan24/
# на сервере:
cd /opt/plan24 && tar xzf plan24.tgz && cd deploy/timeweb
cp .env.example .env && chmod 600 .env && nano .env
```
В `.env` обязательно: `PLAN24_DOMAIN`, `PLAN24_BASE_URL`, `PLAN24_SECRET` (`openssl rand -hex 32`), `PLAN24_DB_URL` (роль `plan24_app`),
`PLAN24_DB_MIGRATE_URL` (`gen_user`, только для миграций), SMTP. Если подключаетесь к БД по домену кластера, а не по приватному IP, —
`sslmode=verify-full&sslrootcert=/certs/ca.crt` и сертификат из панели в `deploy/timeweb/certs/ca.crt`.

## 7. Миграции и запуск
```bash
docker compose run --rm migrate      # применяет схему от имени gen_user (владельца БД)
docker compose up -d                 # caddy + web + scheduler
docker compose ps                    # все сервисы Up
docker compose logs -f web           # ошибки старта: «Схема БД на ревизии…», «обхода RLS…» — см. «Диагностика»
```
Приложение **не стартует**, если схема не на последней ревизии или если оно подключено владельцем/суперпользователем — это намеренно.

## 8. Проверка
```bash
sh postdeploy-check.sh https://plan.example.com
```
Все пункты должны быть «ОК». Затем вручную: регистрация первой организации → письмо с подтверждением пришло → вход → «Начнём → загрузить пример»
(убедитесь, что план строится) → удалите пример или заведите свои данные.

## 9. Резервные копии (сделайте до запуска пользователей)
1. В панели Timeweb включены автоматические копии кластера (шаг 1) — это основной уровень.
2. Дополнительно — логическая копия на ваше хранилище (S3 Timeweb или другое):
   ```bash
   sudo -u plan24 sh -c 'cat > /opt/plan24/deploy/timeweb/backup.env <<EOF
   PGHOST=ПРИВАТНЫЙ_IP
   PGPORT=5432
   PGUSER=gen_user
   PGPASSWORD=ПАРОЛЬ
   PGDATABASE=ИМЯ_БД
   PGSSLMODE=require
   S3_BUCKET=...
   S3_ENDPOINT=...            # адрес из панели хранилища
   AWS_ACCESS_KEY_ID=...
   AWS_SECRET_ACCESS_KEY=...
   EOF'
   chmod 600 /opt/plan24/deploy/timeweb/backup.env
   sudo cp /opt/plan24/deploy/timeweb/plan24-backup.{service,timer} /etc/systemd/system/
   sudo systemctl daemon-reload && sudo systemctl enable --now plan24-backup.timer
   ```
   Копию делает владелец БД (он обходит RLS); роль приложения увидела бы 0 строк.
3. **Проведите учебное восстановление до запуска**: `OWNER_ROLE=gen_user PGUSER=gen_user PGPASSWORD=… PGHOST=… sh deploy/postgres/restore-check.sh /var/backups/plan24/файл.dump`
   (нужна привилегия CREATEDB). Скрипт печатает число таблиц/политик/ревизию и права роли приложения на журнал аудита (должно быть `INSERT,SELECT`).
   Копия, которую ни разу не восстанавливали, — не копия.

## 10. Мониторинг
* Внешняя проверка `https://ВАШ_ДОМЕН/api/v1/health/ready` (200 — всё хорошо; 503 — БД недоступна или схема устарела) — в мониторинге Timeweb или любом внешнем сервисе.
* Диск сервера (образы Docker и логи): `docker system df`, при необходимости `docker system prune`.
* Логи: `docker compose logs --since 1h web`. Тексты писем, сообщений бота и chat_id в логи не пишутся.

## 11. Обновление версии и откат
```bash
# 1) копия:  sh /opt/plan24/deploy/timeweb/backup-to-s3.sh      2) выложить новый релиз в /opt/plan24 (как на шаге 6)
docker compose build && docker compose run --rm migrate && docker compose up -d
sh postdeploy-check.sh https://plan.example.com
```
Откат кода без изменений схемы — вернуть прежний релиз и `docker compose up -d --build`. Откат схемы (`alembic downgrade`) возможен только для обратимых
миграций; если миграция удаляла данные — **восстановление из копии**. Старайтесь писать миграции совместимыми со старой версией кода.

## 12. Telegram с российских серверов
Свежие публикации (Хабр, vc.ru и др., 2026) и обсуждения в проектах сообщают, что доступ к `api.telegram.org` из российских сетей фильтруется,
причём отмечались и серверы за рубежом у российских хостеров. Я не могу проверить это из своей среды — **проверьте с вашего сервера до любой настройки бота**:
```bash
curl -m 10 -s -o /dev/null -w "%{http_code}\n" https://api.telegram.org/bot0/getMe     # 401/404 = достучались; 000/таймаут = недоступно
```
| Результат | Что делать |
|---|---|
| Доступно | Режим вебхука (`docker compose exec web python -m plan24.telegram setup-webhook https://ВАШ_ДОМЕН`) **или** опроса (`--profile telegram-poll`). Опрос не требует входящих соединений от Telegram и надёжнее. |
| Недоступно | Релей за пределами РФ (небольшой сервер с reverse proxy на `api.telegram.org`) и `PLAN24_TG_API_BASE=https://relay.example.com` + режим опроса; либо прокси `PLAN24_TG_PROXY=socks5://…`. Готовый релей для вашего сервера — `deploy/relay/README.md`. |
| Не хотите зависеть | Не включайте Telegram: сервис полностью работает через веб (интерфейс адаптирован под телефон). |

Важно для бизнеса, а не только для техники: даже при работающем сервере **сборщикам нужен доступ к Telegram на телефонах**; если у вас он нестабилен, бот не решит задачу ввода факта.
Сообщения бота содержат имена сотрудников и названия операций и передаются через Telegram (иностранный сервис) — вопрос трансграничной передачи персональных данных
согласуйте с юристом. Альтернатива (например, российский мессенджер с API ботов) в сервисе не реализована.

## 13. Безопасность — чек-лист перед запуском
- [ ] База доступна только из частной сети; публичный IP кластера выключен или ограничен вашими адресами.
- [ ] `.env` и `backup.env` — `chmod 600`, не в репозитории; пароли `gen_user`, `plan24_app` разные и длинные.
- [ ] Приложение работает под `plan24_app` (иначе не стартует); `gen_user` используется только для миграций и копий.
- [ ] Вход по SSH только по ключу; root отключён; fail2ban работает.
- [ ] `PLAN24_ENV=prod` (иначе открыты отладочные маршруты) — `postdeploy-check.sh` это проверяет.
- [ ] Сертификат выпущен (Caddy), HSTS включён, HTTP перенаправляет на HTTPS.
- [ ] Резервное копирование включено **и восстановление проверено**.
- [ ] Согласие на обработку персональных данных при регистрации и политика обработки — подготовлены юристом (в приложении есть только чекбокс).

## 14. Диагностика
| Симптом | Причина / действие |
|---|---|
| web не стартует: «Схема БД на ревизии …» | не выполнены миграции → `docker compose run --rm migrate` |
| web не стартует: «…права обхода RLS…» | в `PLAN24_DB_URL` указан `gen_user` или другой владелец → укажите `plan24_app` |
| migrate: «Роль приложения … не создана» | не выполнен шаг 4 |
| migrate: `permission denied` / `must be owner` | миграции запущены не владельцем БД → проверьте `PLAN24_DB_MIGRATE_URL` и вывод предполётной проверки |
| `/ready` → 503 «База данных недоступна» | сеть/пароль/адрес БД; проверьте `psql` с сервера теми же данными |
| Caddy не выпускает сертификат | A-запись не указывает на сервер или закрыты порты 80/443 |
| Письма не приходят | SMTP-данные; `docker compose logs web \| grep mail` (в логе только тип ошибки и домен получателя); SPF/DKIM |
| Лимит попыток входа «слепой» (у всех один IP) | не доходит `X-Forwarded-For`: запросы идут мимо Caddy, а не через него |

## Что проверено и что нет
**Проверено** (на PostgreSQL 16 в среде разработки, включая эмуляцию управляемой БД без суперпользователя с правами только CREATEROLE/CREATEDB):
предполётный скрипт; создание роли приложения обычным владельцем БД (дважды подряд); миграции от владельца; отказ приложения стартовать под владельцем;
работа под созданной ролью и защита строк (0 строк без контекста организации, владелец видит всё, журнал аудита не изменить); резервная копия и восстановление
с проверкой данных, политик и прав; команды контейнера (`migrate`, `web`) и запуск двумя процессами; `postdeploy-check.sh` (находит ошибочную конфигурацию);
доступ к API Telegram через настраиваемый адрес/прокси и опрос с повтором при сетевых сбоях (на подставном транспорте).

**Не проверено:** сборка Docker-образа и compose-файл (нет Docker); Caddy и выпуск сертификата; реальный кластер Timeweb (права `gen_user`, TLS-сертификат, приватная сеть);
SMTP с шифрованием; реальный Telegram; `bootstrap.sh`, systemd-таймер и выгрузка в S3 (проверен только синтаксис). Первый запуск на настоящей инфраструктуре почти наверняка
выявит мелочи — присылайте вывод команд, разберём.
