# Развёртывание Plan 24 через App Platform (Timeweb Cloud)

Это вариант **без собственного сервера**: приложение запускается платформой из Git-репозитория по `docker-compose.yml`, домен и TLS даёт платформа.
Вариант с собственным облачным сервером (больше контроля, но нужно администрировать ОС) — в `README.md` этого же каталога.

> Условия платформы взяты из документации Timeweb (timeweb.cloud/docs/apps/deploying-with-docker-compose, дата сверки — 7 октября 2026).
> Корневой `docker-compose.yml` проверяется на соответствие этим условиям скриптом `deploy/timeweb/check-apps-compose.py` (и тестом в CI).
> **Сам деплой на платформе в среде разработки проверить нельзя** — раздел «Что проверено» в конце.

## Что создаём в Timeweb

| № | Что | Зачем |
|---|---|---|
| 1 | **Приватная сеть (VPC)** | приложение и база общаются без выхода в интернет |
| 2 | **Облачная база PostgreSQL 16** (DBaaS), подключённая к этой сети | данные; **в App Platform базу не размещаем** |
| 3 | **Приложение App Platform**, тип «Docker Compose», из вашего Git-репозитория, подключённое к той же сети | web + scheduler + Telegram-бот |
| 4 | Ваш **домен** (привязывается к приложению) | адрес сервиса, ссылки в письмах |
| 5 | (необязательно) бакет **S3** | дополнительные резервные копии |

## Что выбрать: App Platform или свой сервер
| | App Platform | Свой облачный сервер |
|---|---|---|
| Администрирование ОС, файрвол, обновления | не нужно | на вас (есть `bootstrap.sh`) |
| Домен и TLS | даёт платформа | Caddy в compose |
| Выкладка | `git push` → автодеплой | вручную `scp` + `docker compose` |
| Доступ в консоль сервера | **нет** | есть |
| Свои расписания (cron/systemd) | **нет** | есть |
| Тома Docker | **запрещены** (нам не нужны: сервис без состояния) | есть |
Для команды без администратора App Platform проще. Если нужен консольный доступ и свои задания по расписанию — свой сервер.

## Шаг 1. Репозиторий
Платформа берёт код из GitHub/GitLab/Bitbucket (или по ссылке). Приватный репозиторий допустим — вы авторизуете Timeweb в своём Git-аккаунте.
```bash
unzip plan24-service.zip && cd plan24
git init -b main && git add . && git commit -m "Plan 24"
git remote add origin git@github.com:ВАШ/plan24.git && git push -u origin main
git checkout -b release && git push -u origin release        # из этой ветки будем деплоить
```
* В репозитории **нет секретов**: все пароли — в «Переменных» приложения (шаг 4). Тест `test_no_secrets_committed_in_deploy_files` это охраняет.
* Деплой из отдельной ветки `release` — чтобы случайный коммит в `main` не запускал миграции на боевой базе (каждый деплой = `alembic upgrade head`).
* `docker-compose.yml` и каталог `deploy/` должны быть в корне, как в архиве.

## Шаг 2. Сеть и база
1. Создайте приватную сеть в нужном регионе (Москва/СПб — 152-ФЗ).
2. Создайте кластер PostgreSQL **16** в этом регионе и этой сети; включите автоматические резервные копии (физические и логические — разделы документации «Физические бэкапы», «Логические бэкапы»). Не минимальный тариф: на нём нельзя создавать пользователей.
3. Запишите: **приватный IP**, имя базы, пользователя кластера (`gen_user`), пароль.

## Шаг 3. Настройка базы (один раз)
У App Platform нет консоли, поэтому эти команды выполняются **с вашего компьютера**, а для этого базе нужно временно разрешить подключение с вашего IP:
1. В панели включите «Доступ по публичному IP» для кластера и ограничьте его **вашим адресом**.
2. Проверка (результат пришлите мне, если есть «НЕТ»):
   ```bash
   psql "postgresql://gen_user:ПАРОЛЬ@ПУБЛИЧНЫЙ_АДРЕС:5432/ИМЯ_БД?sslmode=require" -f deploy/timeweb/db-preflight.sql
   ```
3. Создание роли приложения:
   ```bash
   psql "…то же…" -v ON_ERROR_STOP=1 -v app_pw='ПАРОЛЬ_ПРИЛОЖЕНИЯ' -f deploy/postgres/init-roles-managed.sql
   ```
4. **Снова выключите публичный доступ** к базе. Дальше она доступна только из приватной сети.
Миграции выполнятся сами при деплое (сервис `migrate`).

## Шаг 4. Создание приложения
Панель → App Platform → «Создать»:
1. Репозиторий → ветка **`release`**. Опцию «Сборка по последнему коммиту» можно оставить (автодеплой при push в `release`).
2. Фреймворк: **Docker Compose** (проверьте, что выбран именно он).
3. Регион — тот же, что у базы. Конфигурация сервера — ориентировочно от 2 ГБ памяти (это оценка: web на 2 процесса + scheduler + бот; уточните по графикам панели после запуска).
4. «Расширенные настройки»:
   * **Приватная сеть** — выберите сеть из шага 2 и IP для приложения. **Изменить сеть после деплоя нельзя.** При повторных деплоях с приватным IP возможна кратковременная недоступность.
   * **Переменные** — перенесите из `deploy/timeweb/apps.env.example`: обязательны `PLAN24_SECRET`, `PLAN24_BASE_URL`, `PLAN24_DB_URL` (роль `plan24_app`, **приватный** IP), `PLAN24_DB_MIGRATE_URL` (`gen_user`; получает только сервис `migrate`).
     SMTP — по желанию сразу. Секреты: `openssl rand -hex 32`.
5. Имя, проект — по желанию. «Запустить деплой».

## Шаг 5. Первый деплой
Во вкладке «Деплой» смотрите лог. Ожидаемый порядок: сборка образа → `migrate` (применяет схему и завершается успешно) → запуск `web`, `scheduler`, `tg`.
* Если упал `migrate`: «Роль приложения … не создана» → шаг 3; `permission denied` / `must be owner` → проверьте, что в `PLAN24_DB_MIGRATE_URL` именно владелец БД.
* Если упал `web`: «Схема БД на ревизии…» → миграции не прошли; «…обхода RLS…» → в `PLAN24_DB_URL` указан не `plan24_app`.
* Если сразу ошибка `PLAN24_… обязателен`/пустые значения: платформа не подставила переменные панели в compose — это допущение, которое я проверить не мог (см. конец); сообщите, исправим способ передачи.
Адрес и технический домен — на вкладке «Дашборд». Откройте `https://ТЕХДОМЕН/api/v1/health/ready` → `{"status":"ready","database":"postgresql"}`.

## Шаг 6. Домен и письма
1. Привяжите свой домен (инструкция Timeweb «Привязка домена»), убедитесь, что сертификат выдан.
2. Измените `PLAN24_BASE_URL` на итоговый `https://…` и перезапустите деплой: **ссылки в письмах строятся из него**.
3. Укажите в настройках приложения «Путь проверки состояния» = `/api/v1/health` (живость). Не `/ready`: кратковременная недоступность БД не должна приводить к перезапуску приложения (поведение платформы при сбое проверки я не проверял).

## Шаг 7. Проверка
```bash
sh deploy/timeweb/postdeploy-check.sh https://ВАШ_ДОМЕН
```
Ошибок быть не должно. «ВНИМАНИЕ: HTTP не перенаправляется на HTTPS» — предупреждение: платформа сообщает лишь, что порт 80 открыт; HSTS защищает повторные заходы, а письма ведут на https.
Дополнительно с вашего компьютера: `curl -m 5 http://ПУБЛИЧНЫЙ_IP_ПРИЛОЖЕНИЯ:8000/api/v1/health` — **не должно отвечать**. Если отвечает, приложение доступно в обход TLS напрямую по порту контейнера; сообщите мне — решим (поддержка Timeweb или вариант со своим сервером).
Затем вручную: регистрация → письмо с подтверждением → вход → «Загрузить пример» → план строится.

## Шаг 8. Telegram (необязательно)
У платформы нет консоли, поэтому доступ к Telegram проверяется через бота:
1. Установите `PLAN24_TG_TOKEN`, `PLAN24_TG_SECRET`, `PLAN24_TG_BOT_USERNAME`, `PLAN24_TG_MODE=poll` и перезапустите деплой.
2. В логе сервиса `tg`: тишина — бот опрашивает Telegram; повторяющиеся `getUpdates failed: ConnectError/ConnectTimeout` — доступ закрыт. Тогда релей/прокси за пределами РФ: `PLAN24_TG_API_BASE` или `PLAN24_TG_PROXY`.
3. Режим `webhook` на платформе нужен только если Telegram может достучаться до вашего домена; опрос надёжнее.
Помните: сборщикам нужен рабочий Telegram на телефонах (см. `README.md`, раздел «Telegram с российских серверов»).

## Шаг 9. Резервные копии
Основной уровень — автоматические копии кластера в панели (шаг 2) — **проверьте восстановление до запуска пользователей**: восстановите копию в отдельную базу/кластер (по инструкции Timeweb) и убедитесь, что приложение под `plan24_app` видит данные организации.
Собственная выгрузка по расписанию (`backup-to-s3.sh`) на платформе без консоли и cron не запускается; при необходимости её можно оформить отдельным сервисом compose — сделаем по запросу.

## Шаг 10. Обновление и откат
* Обновление: **копия БД** → слияние в `release` → автодеплой (сборка → `migrate` → перезапуск) → `postdeploy-check.sh`.
* Откат кода: выберите прежний коммит (опция ручного выбора коммита в настройках деплоя). Откат схемы — только для обратимых миграций; иначе восстановление из копии.

## Безопасность — что учесть именно на платформе
* Секреты только в «Переменных»; в репозитории их нет.
* Пароль владельца БД (обходит защиту строк) получает **только** сервис `migrate`; web, scheduler и бот его не видят (проверено тестом).
* **IP клиента.** Приложение не доверяет заголовку `X-Forwarded-For` (адрес прокси платформы мне неизвестен, а слепое доверие позволило бы подделывать IP). Поэтому ограничение попыток входа работает **по e-mail**, а не по паре e-mail + IP: злоумышленник может временно блокировать вход конкретному пользователю, но не обойти лимит сменой IP.
* Публичный доступ к БД выключен после шага 3. Приложение работает только под `plan24_app`, под владельцем оно не запускается.
* Вход в панель Timeweb защитите двухфакторной аутентификацией.

## Диагностика: код выхода `migrate`
Платформа в логе деплоя показывает только строку вида `service "migrate" didn't complete successfully: exit N`. Контейнер миграций сам проверяет подключение и возвращает свой код:

| Код | Причина | Что сделать |
|---|---|---|
| 10 | не задана или не разобрана `PLAN24_DB_MIGRATE_URL` / `PLAN24_DB_URL` | проверьте «Переменные»; в пароле только буквы и цифры |
| 12 | нет сети до БД | адрес и порт; **приватный** IP; приложение и БД в одной приватной сети |
| 13 | неверный пароль или пользователь владельца БД (`gen_user`) | пароль в `PLAN24_DB_MIGRATE_URL` |
| 14 | проблема с SSL | `sslmode=require` в адресе |
| 15 | базы с таким именем нет | имя базы в адресе |
| 16 | **роль приложения не создана** | создайте пользователя `plan24_app` в панели (раздел «Пользователи») |
| 17 | роль есть, но пароль в `PLAN24_DB_URL` не подошёл | пароль `plan24_app` |
| 18 | роль приложения не подключилась по другой причине | лог контейнера |
| 19 | сервер БД не пускает с этого адреса | та же приватная сеть, приватный IP |
| 20 | сами миграции завершились ошибкой | лог контейнера `migrate` |
| 21 | у владельца нет права создавать таблицы в `public` | права `gen_user` |

| Симптом | Действие |
|---|---|
| Деплой падает на сборке | лог сборки; чаще всего нет файла из `COPY` в Dockerfile (тест `test_dockerfile_matches_compose_build_context` это ловит) |
| «Ошибка манифеста» при деплое | директива из списка запрещённых; запустите `python3 deploy/timeweb/check-apps-compose.py` |
| web не получает переменные | см. шаг 5; пришлите лог |
| `/ready` → 503 | БД недоступна из приватной сети: IP, пароль, та же ли сеть у приложения и базы |
| Письма не приходят | SMTP-переменные; в логе `web` — тип ошибки и домен получателя |
| Приложение недоступно после деплоя | при приватном IP короткая пауза на деплое — нормально; затянулась — лог деплоя |

## Что проверено и что нет
**Проверено:** `docker-compose.yml` соответствует запретам и условиям из документации Timeweb (скрипт-проверка + тесты, включая негативные); все переменные compose описаны в примере для панели;
пароль владельца БД есть только у `migrate`; `COPY` в Dockerfile ссылается на существующие файлы; зависимости образа ставятся с нуля и приложение импортируется; команды контейнера
(`migrate`, `web`, `tg`), сам путь установки на PostgreSQL без суперпользователя, защита строк, резервное копирование/восстановление — на PostgreSQL 16; HSTS и заголовки безопасности.
**Не проверено (нужна ваша среда):** сборка образа и работа compose (в среде нет Docker); поведение именно этой платформы — подстановка переменных панели в compose, поддержка
`depends_on: service_completed_successfully`, реакция на проверку состояния, доступность порта контейнера снаружи, редирект HTTP→HTTPS, подключение к DBaaS по приватной сети;
реальный Telegram; SMTP с шифрованием. Первый деплой почти наверняка выявит мелочи — присылайте лог деплоя.
