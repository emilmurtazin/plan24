# Telegram через сервер за пределами РФ (релей)

Бот Plan 24 уже написан: привязка по одноразовому коду, задания дня, ввод факта кнопкой или числом, причины отклонений,
отмена последнего ввода, утренние задания и вечерние напоминания. Не хватает только **пути до Telegram**, потому что с российских
серверов `api.telegram.org` фильтруется. Этот набор ставит на ваш сервер в Нидерландах (**72.56.68.43**, IPv6 `2a03:6f02::1:2496`)
маленький релей, через который основной сервер разговаривает с Telegram.

> **Если на сервере уже работают другие сервисы (вебхуки и т. п.) — они не затрагиваются.** Релей ставится как **отдельная служба
> `plan24-relay`**: свой экземпляр nginx со своим конфигом (`/etc/plan24-relay`), своим пользователем и **своим портом (9443 по умолчанию)**.
> Скрипт не меняет и не перезагружает ваши nginx/Caddy/Apache, не занимает порты 80/443 и не трогает чужие сертификаты и вебхуки.
> Перед установкой есть команда, которая **только смотрит** и ничего не меняет (`preflight-relay.sh`), а после — полное удаление (`uninstall-relay.sh`).
> Проверено на сервере с работающим nginx и двумя вебхук-сервисами (один на 443 как `default_server`): процесс и файлы nginx не изменились,
> ответы сервисов те же до и после установки и после удаления.

## Как это устроено

```
 телефон работника ⇄ Telegram ⇄ [сервер в Нидерландах: nginx-релей] ⇄ HTTPS ⇄ [основной сервер Plan 24: tg + scheduler]
```

* **Всё идёт в одну сторону — от основного сервера к релею.** Бот работает в режиме *опроса* (`PLAN24_TG_MODE=poll`):
  основной сервер сам, через релей, постоянно (long polling) забирает сообщения работников и через него же отправляет ответы
  и уведомления. Входящих соединений на основной сервер не нужно, вебхук не нужен, никакой переадресации обратно нет.
* Релей — это nginx, который **пропускает только запросы вашего бота** (адрес содержит токен бота), всё остальное получает 404.
  Открытым прокси он не является.
* Шифрование: на сервере создаётся **самоподписанный сертификат на ваши IP-адреса**, а основной сервер **доверяет только ему**
  (закрепление сертификата, `PLAN24_TG_CA_PEM`). Домен и Let's Encrypt не нужны, подмена релея невозможна.
* Токен бота в журналы доступа nginx не попадает (`access_log off`).

## Что нужно заранее

1. **Бот.** В Telegram откройте `@BotFather` → `/newbot` → получите **токен** (`123456789:AA…`) и имя бота (`my_plan_bot`).
2. **Секрет** (любая случайная строка, понадобится основному серверу): `openssl rand -hex 24`.
3. Доступ `root` по SSH к серверу в Нидерландах (Ubuntu/Debian). Порт релея (**9443/tcp**) должен быть открыт в панели хостера, если там есть
   внешний файрвол (скрипт сам откроет его в `ufw`, если тот включён; одно правило, удаляется при `uninstall-relay.sh`).

## Шаг 1. Релей на сервере в Нидерландах

Скопируйте папку `deploy/relay` на сервер (`scp -r deploy/relay root@72.56.68.43:/root/`).

**1a. Посмотрите, что на сервере уже есть (ничего не меняет):**

```bash
cd /root/relay
bash preflight-relay.sh
```

Покажет, какие порты и веб-серверы заняты, и скажет, свободен ли порт релея. Если 9443 занят вашим сервисом — выберите другой порт:
`LISTEN_PORT=9444 bash preflight-relay.sh` (и дальше с тем же `LISTEN_PORT`). Установка в любом случае **откажется** занимать чужой порт.

**1b. Установка:**

```bash
BOT_TOKEN='123456789:AAxxxxxxxx' RELAY_IPS="72.56.68.43 2a03:6f02::1:2496" bash setup-relay.sh
```

Скрипт: создаёт отдельного пользователя и службу `plan24-relay`, сертификат и конфиг релея, запускает его и **печатает две строки для основного сервера**. Пакет nginx ставится только если его на сервере вообще нет (и стандартная служба nginx при этом отключается); если nginx уже есть — он остаётся нетронутым:

```
PLAN24_TG_API_BASE=https://72.56.68.43:9443
PLAN24_TG_CA_PEM=LS0tLS1CRUdJTiBDRVJUSUZJQ0FURS0tLS0t…
```

Если на основном сервере IP постоянный, добавьте `ALLOW_FROM="АДРЕС_ОСНОВНОГО_СЕРВЕРА"` — тогда релей не пустит никого другого.
(На платформах вроде Timeweb Apps исходящий адрес может меняться — тогда не задавайте: защитой остаются токен и закреплённый сертификат.)

Проверка прямо на этом сервере:

```bash
BOT_TOKEN='123456789:AAxxxxxxxx' bash relay-check.sh
```

Ожидается `ВСЁ В ПОРЯДКЕ`: Telegram достижим с сервера; релей отвечает по TLS; `getMe` через релей возвращает вашего бота; чужой путь даёт 404.

## Шаг 2. Настройки основного сервера

Добавьте переменные окружения (в `.env` или в настройках приложения на платформе) сервисам `tg` и `scheduler`
(в `docker-compose.yml` в корне проекта они уже передаются):

| Переменная | Значение |
|---|---|
| `PLAN24_TG_MODE` | `poll` |
| `PLAN24_TG_TOKEN` | токен от BotFather |
| `PLAN24_TG_SECRET` | случайная строка из «Что нужно заранее» |
| `PLAN24_TG_BOT_USERNAME` | имя бота без `@` |
| `PLAN24_TG_API_BASE` | `https://72.56.68.43:9443` (то, что напечатал скрипт) |
| `PLAN24_TG_CA_PEM` | длинная строка base64 (то, что напечатал скрипт) |
| `PLAN24_TG_MORNING_AT`, `PLAN24_TG_EVENING_AT` | необязательно: время утренних заданий и вечернего напоминания (по умолчанию `07:30` и `17:30`, по часовому поясу организации) |

Перезапустите сервисы (`docker compose up -d`, на платформе — передеплой).

> Адрес на IPv6 тоже работает (`PLAN24_TG_API_BASE=https://[2a03:6f02::1:2496]:9443`), но IPv4 надёжнее: не все основные серверы имеют IPv6.

## Шаг 3. Проверка связи с основного сервера

В логе сервиса `tg` при каждом старте печатается итог проверки:

```
Telegram: путь — релей 72.56.68.43, сертификат релея закреплён
✔ Telegram доступен (180 мс), бот @my_plan_bot
```

Если есть консоль: `docker compose exec tg python -m plan24.telegram check` (то же + состояние вебхука; код выхода 0 — всё хорошо).
Если вместо этого `✘ Telegram недоступен: …` — причина написана по-русски (см. «Если не работает»).

## Шаг 4. Привязка работников и ввод факта

1. В Plan 24: **Работники → Работники** (для бригадира — **Организация → Пользователи**) → у человека кнопка **«Telegram»** → «Выдать код».
2. Передайте код человеку. Он открывает бота в Telegram и отправляет `/start КОД`. Код одноразовый, действует сутки.
3. Дальше у него в боте:
   * `/tasks` — задания на сегодня; кнопка «всё» вносит выполнение полностью, либо отправляется число (бот переспрашивает для подтверждения);
   * бот предлагает выбрать причину отклонения — из причин **участка работника** и общих;
   * `/undo` — отменить последний ввод; `/cancel` — отменить текущий;
   * у бригадира `/queue` — факт, ожидающий подтверждения.

## Уведомления от сервиса

Сервис `scheduler` (уже есть в compose) каждые 60 секунд проверяет время и отправляет привязанным людям:

* **утром** — задания на день (`PLAN24_TG_MORNING_AT`, по умолчанию 07:30);
* **вечером** — напоминание внести факт, если он не внесён (`PLAN24_TG_EVENING_AT`, по умолчанию 17:30).

Каждому — не чаще раза в сутки на вид уведомления; если сервис был выключен, «догоняет» только в течение 3 часов после назначенного времени.

## Если не работает

| В логе / проверке | Причина и что делать |
|---|---|
| `ConnectTimeout` / «релей не отвечает» | Порт релея закрыт: файрвол хостера (откройте TCP 9443 в панели) или `ufw allow 9443/tcp`; для `ALLOW_FROM` — адрес основного сервера указан неверно. Проверьте с основного сервера: `curl -m 8 -k https://72.56.68.43:9443/healthz` → `ok`. |
| `ConnectError`, «сертификат релея не принят» | В `PLAN24_TG_CA_PEM` не тот сертификат (после повторной установки на релее выпустился новый — скопируйте строку, которую напечатал скрипт), либо адрес в `PLAN24_TG_API_BASE` не совпадает с IP в сертификате. |
| `404: релей или Telegram не знает этот токен` | Токен в `PLAN24_TG_TOKEN` отличается от того, с которым ставили релей. Повторите `setup-relay.sh` с правильным токеном. |
| `401: Telegram не принял токен` | Токен отозван или с опечаткой (BotFather → `/token`). |
| `502/503/504 … релей не достаёт до Telegram` | С сервера релея нет связи с Telegram: `relay-check.sh`, пункт 1. Бывает на «серых» хостингах — попробуйте другой сервер. |
| Бот молчит, а в логе `✔ Telegram доступен` | Работник не привязан (бот ответит «чат не привязан»), либо запущены одновременно `poll` и установленный ранее вебхук: `python -m plan24.telegram delete-webhook`. |

## Обслуживание

* **Состояние релея:** `systemctl status plan24-relay`; перезапуск — `systemctl restart plan24-relay`. Это отдельная служба: перезапуск и остановка релея ваши другие сервисы не затрагивают.
* **Сменить токен бота:** `BOT_TOKEN='новый' bash setup-relay.sh` на релее (сертификат сохраняется) и новый `PLAN24_TG_TOKEN` на основном сервере.
* **Перевыпустить сертификат** (по умолчанию он действует 10 лет): `rm /etc/plan24-relay/relay.crt`, запустите `setup-relay.sh` заново и замените `PLAN24_TG_CA_PEM`.
* **Полностью убрать релей:** `bash uninstall-relay.sh` — удаляет службу, конфиг, сертификат, журналы, пользователя и правило ufw. Пакет nginx и всё остальное на сервере остаётся как есть.
* Журнал ошибок релея: `/var/log/plan24-relay/error.log` (в строках ошибок nginx может встретиться токен — не публикуйте его).

## Важное

* Сообщения бота содержат имена сотрудников и названия операций и проходят через Telegram (иностранный сервис) и ваш релей —
  это вопрос трансграничной передачи персональных данных; решение за вами.
* Сборщикам нужен рабочий Telegram на телефонах: релей решает доступ **сервера**, а не телефонов.
* Один релей — одна точка отказа: если сервер в Нидерландах недоступен, бот молчит, а веб-интерфейс продолжает работать (факт можно вносить там).
