# Plan 24 — сервис планирования производства (Модуль 1)

Компании регистрируются, заводят изделия, операции, исполнителей и заказы прямо в сервисе, вносят факт и получают
план по дням на каждого сборщика. Excel в основном сценарии не используется.

## Запуск
```bash
cd backend && pip install -r requirements.txt
python3 -m uvicorn plan24.app:app --port 8000        # интерфейс http://localhost:8000, документация API /api/docs
```
Локально: `PLAN24_ENV=dev python3 -m uvicorn plan24.app:app` (по умолчанию режим `prod`: нужен `PLAN24_SECRET`, отладочных возможностей нет).

| Переменная | Назначение |
|---|---|
| `PLAN24_ENV` | `prod` (по умолчанию) или `dev` |
| `PLAN24_SECRET` | подпись токенов; **обязателен** в prod (в dev создаётся сам) |
| `PLAN24_DB_URL` | БД приложения: `postgresql+psycopg://plan24_app:…@host/plan24` (боевой режим) или SQLite (по умолчанию, разработка) |
| `PLAN24_DB_MIGRATE_URL` | подключение **владельца схемы** для миграций (`alembic upgrade head`) |
| `PLAN24_DB_POOL`, `PLAN24_DB_OVERFLOW` | размер пула соединений |
| `PLAN24_DATA` | каталог данных SQLite |
| `PLAN24_BASE_URL` | публичный адрес сервиса для ссылок в письмах (`https://plan.example.com`) |
| `PLAN24_SMTP_HOST`, `_PORT`, `_USER`, `_PASSWORD`, `_SECURITY` (`starttls`/`ssl`/`none`), `PLAN24_MAIL_FROM` | отправка писем; без `PLAN24_SMTP_HOST` письма пишутся в файлы `data/outbox` (только разработка) |
| `PLAN24_TG_TOKEN`, `PLAN24_TG_SECRET`, `PLAN24_TG_BOT_USERNAME` | Telegram-бот (токен от @BotFather, случайный секрет вебхука, имя бота) |
| `PLAN24_TG_API_BASE`, `PLAN24_TG_PROXY`, `PLAN24_TG_CA_PEM` | адрес API Telegram (релей), прокси и сертификат релея (PEM или base64) — если `api.telegram.org` недоступен с вашего сервера |
| `PLAN24_TG_MODE` | режим бота в App Platform: `off` (по умолчанию) / `poll` / `webhook` |
| `PLAN24_DOCS=1` | опубликовать описание API (`/api/docs`) в prod; по умолчанию в prod скрыто |
| `PLAN24_TG_MORNING_AT`, `PLAN24_TG_EVENING_AT` | время утренних заданий и вечернего напоминания, по часовому поясу организации (07:30 / 17:30) |
| `PLAN24_TODAY` | только dev: зафиксировать «сегодня» |
| `PLAN24_METRIKA_ID` | номер счётчика Яндекс.Метрики для лендинга `/welcome` (только цифры); без него аналитика не подключается и внешних запросов нет |

### Подключение Telegram-бота
1. Создайте бота у @BotFather, задайте `PLAN24_TG_TOKEN`, `PLAN24_TG_SECRET` (длинная случайная строка), `PLAN24_TG_BOT_USERNAME`.
**Если `api.telegram.org` недоступен с вашего сервера — используйте релей на сервере за пределами РФ: готовый набор и пошаговая инструкция — `deploy/relay/README.md` (`setup-relay.sh`, `relay-check.sh`; связь основного сервера с релеем закрепляется сертификатом, `PLAN24_TG_CA_PEM`). Проверка связи: `python -m plan24.telegram check`.**
2. Сервис должен быть доступен по HTTPS: `python -m plan24.telegram setup-webhook https://plan.example.com`
   (без публичного адреса: `python -m plan24.telegram poll` — бот сам опрашивает Telegram).
3. Напоминания: `python -m plan24.telegram scheduler` (отдельный процесс) или `notify` по cron каждые 5–10 минут.
4. В «Данные → Исполнители» (или «Пользователи» для бригадира) нажмите «Telegram → Выдать код» и передайте код человеку.

## Лендинг для рекламы
Страница `/welcome` (файлы — `frontend/landing/`) открывается без входа. Кнопки ведут на `/#register` (форма регистрации) и переносят метки
рекламы (`utm_*`, `yclid`, `gclid`, `vkclid`…) в адрес. Для Яндекс.Метрики задайте `PLAN24_METRIKA_ID`: на странице появятся цели
`cta_click` (клик «Создать организацию»), `login_click`, `scroll_60`. Перед запуском рекламы добавьте на страницу ссылки на оферту и политику
обработки персональных данных (в сервисе таких страниц пока нет).

## PostgreSQL (боевой режим)
Подробно — `docs/OPERATIONS.md`. Кратко: `deploy/postgres/init-roles.sql` → `alembic upgrade head` (владелец) → приложение под ролью `plan24_app`.
Защита на уровне строк (RLS) — вторая линия обороны: даже при забытом в коде фильтре по организации база не отдаёт чужие строки.
Прогон всего набора на PostgreSQL: `PLAN24_TEST_PG_SUPER_URL=postgresql+psycopg://postgres:…@localhost/postgres python3 -m pytest tests -q`
(создаёт БД `plan24_test`, применяет миграции, тесты идут под ролью без обхода RLS). Готовая сборка — `deploy/docker-compose.yml` (**не проверялась: нет Docker**).

**Timeweb Cloud:** два варианта — через **App Platform** (`deploy/timeweb/APPS.md`, корневой `docker-compose.yml`) или на своём облачном сервере (`deploy/timeweb/README.md`); проверочные скрипты и compose под управляемый PostgreSQL.

## Что сделано
- Организации, регистрация (согласие на обработку ПД), вход, refresh-токены с ротацией и обнаружением кражи, лимит попыток входа.
- Строгая изоляция организаций: фильтр по организации везде, проверка ссылок между сущностями, 404 вместо 403 на чужие записи.
- Данные: проекты, изделия + маршруты с версиями, операции (норма, квалификация, порядок/параллельность, блокировка с датой снятия),
  позиции заказов, исполнители, участки, отпуска, допуски к позициям, праздники, причины отклонений.
- Планировщик (`plan24/planner`, чистый Python): перенос Code_v3.5.gs, паритет с оригиналом проверяется эмулятором скрипта.
- План: снапшоты, один активный, откат, флаг «данные изменились после расчёта», заморозка ближайших дней, сравнение вариантов жёсткости.
- Факт: итог дня по исполнителю (повторный ввод заменяет), идемпотентность, подтверждение бригадиром, причины отклонений.
- Перепланирование участка: исполнители других участков и их назначенная работа остаются как есть.
- Письма: подтверждение e-mail, сброс пароля, приглашение сотрудника (SMTP; проверено на реальном SMTP-сервере).
- Telegram-бот: привязка по одноразовому коду (без пароля), задания дня, ввод факта кнопкой «всё» или числом с подтверждением, причины отклонений, «отменить последнее», очередь подтверждений бригадира, утренние задания и вечерние напоминания.
- Отчёты: план на день с фактом, статусы заказов, тепловая карта загрузки, обзор. Журнал изменений.

## Доработки (по списку «Доработки.txt»)
**Этап 1 — сделано:** вкладка «Дашборд» (бывший «Обзор»); новое меню «Каталог изделий», «Проекты и Заказы», «Организация» (участки, работники, календарь, пользователи, журнал, причины отклонений); настройки планировщика — кнопка в «Организация → Участки»;
перепланирование только по участкам (исключение — первый расчёт, когда плана ещё нет: он строится сразу по всем участкам); роль «Технолог» (создаёт и редактирует каталог изделий); «Заказчик» и выбор версии изделия в заказе.
**Этап 2 — сделано:** «Каталог изделий»: у версии маршрута есть название (задаётся при создании, переименовывается и у версии, уже стоящей в заказах), таблица изделий показывает текущую версию, число версий и операций; операции показывают норму, требуемую квалификацию и количество на изделие; название операции можно менять и в используемой версии (норму, порядок, квалификацию — только в новой версии).
Уровни квалификации настраиваются в «Организация → Об организации» (от 1 до 10, с названиями); у работника и у операции квалификация выбирается из этого списка; уровень, который кто-то использует, убрать нельзя. Миграция `0004`.
**Этап 3 — сделано:** в «Проекты и Заказы → Заказы» у каждой позиции есть кнопка «По участкам» и колонка «Операции по участкам»: для каждой операции отмечаются участки (можно несколько). Операция выполняется только работниками своих участков; **операция без участка — ошибка** (`NOT_DISTRIBUTED`): она не попадает в план, следующие за ней операции тоже не планируются, на дашборде красная ошибка с кнопкой «Распределить». Бригадир видит только операции своего участка и только позиции, где они есть. Миграция `0005` (таблица `order_line_operations` с RLS).
**Этап 4 — сделано («План на день»):**
— правка плана вручную: «+ Задание» (можно несколько операций на день), «Изменить» (работник, день, заказ, операция, количество; заказ выбирается с фильтрами по проекту и изделию), «Убрать»;
— **закрепление:** любая правка закрепляет день работника — перепланирование участка его не меняет (в том числе удаление задания); кнопка «Снять закрепление» возвращает день планировщику; откат плана восстанавливает закрепления из возвращаемого плана;
— «+ Работа вне перечня»: работа по заказу (но без операции в маршруте) или не по заказу (уборка, наладка), учёт в часах, свой факт;
— «+ Работник»: временный работник сохраняется в списке работников, но автопланировщик заказов ему не даёт (поле «Участвует в автопланировании» в «Организация → Работники»);
— факт: понятная форма («Сделано», «Всё: N», «Не делали», «Записать выполнение»), причина или комментарий запрашиваются **только** при отклонении — факт меньше плана или выполнено больше, чем нужно по заказу; кнопка «Всё по плану» на работника.
Миграция `0006` (закрепления дней, работы вне перечня, флаги работника).
**Этап 5 — сделано («Статус заказов» переделан):** выбирается заказ; по каждой операции показаны: выполнено из нужного, распланировано, не в плане, **рабочих смен до завершения**, **дата завершения**, отметка **узкого места**, **проблемы** (не распределена по участкам, нет работников нужной квалификации, блокировка, опоздание, нет места в горизонте, повторяющиеся причины отклонений) и **рекомендации** (сколько работников добавить, кто подходит, что устранить). Ниже — таблица всех заказов. Участок видит только свои операции. Эндпоинт `GET /reports/order-status`.
**Этап 6 — сделано («Дашборд»):** выполнение в процентах и по заказам; статусы заказов (полоса, риск опоздания, ближайшие сроки, переход в «Статус заказов»); **потребность в ресурсах** по участкам (сколько работников добавить, нехватка квалификации, недели перегрузки); **повторяющиеся причины отклонений** за 90 дней (где, сколько раз, комментарии); **работники по участкам и по квалификациям**; **график загрузки участков на 3 месяца вперёд** и **график недовыполнения плана за 3 месяца назад** (SVG, с таблицей данных). Бригадир видит только свой участок. Для недовыполнения сохраняются **снимки плана по дням** (`day_plan_snapshots`, миграция `0007`): при перепланировании, ручной правке, раз в сутки при первом открытии дашборда и в планировщике рассылок; история копится с момента выкатки.
**Этап 7 — сделано («Доработки 2», UX):**
— **навигация:** главная страница — «Дашборд»; остальные разделы — в боковом выпадающем меню (☰). «Выполнение» = подвкладки «План на день» и «Загрузка»; «Работники» (сразу после «Выполнения») = подвкладки «Участки», «Работники», «Причины отклонений». Кнопка «Перепланировать» — в верхней панели справа от названия раздела (на дашборде и в «Выполнении»);
— **дашборд:** пять показателей — проектов в работе (есть незавершённые позиции с внесённым фактом), в очереди (факта ещё нет), с риском срыва сроков (есть позиция «Риск опоздания»), работников с заданиями сегодня из общего числа, средняя загрузка на ближайшие 3 месяца; сообщение «кто уже загружен сегодня» убрано; «Статус заказов» — одна таблица заказов со сроком завершения в ближайший месяц (плюс просроченные незавершённые), клик открывает заказ;
— **«План на день»:** кнопки «Печать» нет; правки **ничего не закрепляют сами** — день закрепляется кнопкой «Закрепить день» (`POST /plan-day/pins`), снимается «Снять закрепление»; в уже закреплённом дне новые и изменённые задания остаются закреплёнными;
— **«Загрузка»:** по участкам, в процентах рабочего дня, окно две недели со стрелками; цвет — выполнение плана за день: зелёный — выполнено/перевыполнено, жёлтый — недовыполнение 5–30%, красный — более 30%; дни без факта (будущее, сегодня до ввода факта) — нейтральные;
— **«Статус заказов»:** «Все заказы» сверху, списков «изделие/заказ», печати и комментария под таблицей нет; вместо календарных смен — **человеко-смены до завершения** операции: остаток / (норма × средняя производительность работников операции × коэффициент эффективности) (`person_shifts_left`);
— **профиль:** имя, фамилия, e-mail (смена требует пароль и заново запрашивает подтверждение), пароль; сообщение о неподтверждённой почте перенесено сюда (`PATCH /auth/profile`);
— **пользователи:** имя и фамилия — отдельные поля (миграция `0008`; `name` остаётся полным именем), роль «Директор», переименованы «Администратор» и «Руководитель проекта»; **загрузка из файла** пользователей (`POST /users/import`) и изделий каталога (`POST /products/import`): CSV/TSV/TXT, проверка без сохранения, при ошибке в любой строке не загружается ничего, шаблон скачивается в окне.
Работа вне перечня по-прежнему не учитывается планировщиком, пока день не закреплён вручную.

**Этап 8 — сделано (доработки по результатам просмотра):**
— **не более 100% дня:** планировщик больше не берёт операцию целиком, если она не влезает в остаток дня (раньше при остатке ≥ `min_start_share` хвост «переливался» на следующий день, и день выглядел перегруженным), и учитывает факт сегодняшнего дня как уже занятую часть. Включается флагом `cap_load` движка (сервис включает его всегда; эталонный движок по умолчанию работает как исходный скрипт — сверка `test_parity` не меняется). Единица дольше целого дня стартует только со свободного дня. Ручные и закреплённые правки не ограничиваются — решает человек;
— **«Загрузка»:** в клетке «план / факт» в % дня и две полосы (план и факт), цвет — отставание от плана; справа итоги по работнику за период (план, факт, отставание), у участка — то же в заголовке; сверху сводка по всем;
— **причины отклонений — у каждого участка свои** (`fact_reasons.work_center_id`, миграция `0009`): вкладка с выбором участка; причина без участка — «общая», видна всем (так остались все прежние причины и заведённые по умолчанию). При вводе факта (веб, Telegram) предлагаются причины участка работника и общие; причину чужого участка сервер не принимает. Имя уникально в пределах участка;
— **«Статус заказов»:** в таблице «Все заказы» колонки «Выполнено, %» и «Простой, % (план − факт)». Простой = Σ max(0, план − факт) / Σ план по прошедшим дням в нормо-днях (`idle_pct`; сегодня не входит; плана за прошлое нет — «—»).
Работник без участка не попадает в перепланирование по участкам — у каждого работника должен быть участок.

## Что пока нет (этапы C–E ТЗ)
Отчёт по проекту, автоматическое планирование ресурсов (сейчас — оценка потребности на дашборде и в статусе заказов), ввод факта через Telegram
с выбором операции вне плана, уведомления о риске опоздания и перегрузке (FR-37), тарифы и оплата, асинхронные задачи (перепланирование синхронное),
лендинг, юридические документы, двухфакторная аутентификация.

## Известные ограничения
- Docker-образ и compose-файл написаны, но не собирались и не запускались (в среде разработки нет Docker); проверены по частям: команды контейнера, инициализация ролей, миграции, резервное копирование и восстановление. PostgreSQL проверялся только версии 16.
- Refresh-токен хранится в `localStorage` (переживает перезагрузку, уязвим при XSS; CSP запрещает внешние и inline-скрипты, весь вывод экранируется).
- Telegram-бот проверен на поддельном клиенте и на запросах к Bot API через mock-транспорт, **но не против настоящего Telegram**; SMTP проверен без шифрования, режимы STARTTLS/SSL — нет.
- Интерфейс проверялся в jsdom, не в реальных браузерах, мобильную вёрстку глазами никто не смотрел.
- Расхождения ТЗ и скрипта, дефекты оригинала и принятые решения — `docs/DEVIATIONS.md`.

**Этап 9 — сделано (факт за прошлые дни, нерабочие дни, бригадир):**
— **факт за прошлые дни.** На любой прошедший день в «Плане на день» показано, что на него планировалось (по снимкам плана), и можно внести факт. Сверху — кнопки дней, где факт ещё не внесён (`missing` в `/reports/day`: связка день × позиция × операция × работник без записи факта; внесённый ноль — это внесённый факт), рядом выбор любой даты; на дашборде — баннер «Не внесён факт за прошедшие дни» с переходом к самому раннему. Работа, которой не было в плане, вносится кнопкой «+ Факт вне плана». Сборщик, как и раньше, вносит факт только за сегодня — за прошлые дни обращается к бригадиру;
— **работа в нерабочие дни.** Выходной и праздник (по рабочим дням недели и календарю организации) выбираются как обычная дата. Планировщик в такие дни никого не загружает, поэтому добавленное вручную задание **закрепляется автоматически** (это единственное исключение из правила «закрепление — только вручную»): иначе перепланирование его бы убрало. Закреплённая работа в нерабочий день вычитается из потребности (не планируется второй раз на рабочие дни) и попадает в список дней плана и в «Загрузку». Работа вне перечня в выходной работает и без закрепления;
— **бригадир (руководитель участка)** видит и ведёт работников своего участка: «Работники → Работники» (подвкладок «Участки» и «Причины» у него нет), создание — сразу на его участок, правка, отпуска/отсутствия, коды привязки Telegram своих работников. Нельзя: удалять работников, переводить на другой участок (это права руководителя проекта и администратора), «Допуски» по заказам. Чужие работники для бригадира «не существуют» (404).

**Этап 10 — сделано (Telegram: удобство для сборщика и бригадира).** Бот переработан так, чтобы почти ничего не печатать:
— **постоянное меню внизу экрана** и список команд по роли (кнопка «/»): сборщик — «Задания, Закрыть день, Проблема, Не выйду, Завтра, Настройки»; бригадир — «По людям, Закрыть день, Очередь, Отсутствие, Завтра, Настройки». Меню появляется при привязке и по `/start`, `/help`; у уже привязанных людей — после `/start`;
— **экраны переписываются на месте**, чат не превращается в ленту: список заданий, **карточка задания** (кнопки «＋1 ＋5 ＋10», «Всё», «0 — не делал», «Ввести число»; факт накапливается в течение дня; причина отклонения — прямо в карточке, из причин участка работника), «↩ Отменить последнее» на каждом экране;
— **«Закрыть день по плану»** — одной кнопкой внести плановое по всем заданиям без факта (с подтверждением и списком; уже внесённое не перезаписывается). У бригадира — по одному работнику или по всему участку;
— **бригадир:** экран **«По людям»** (кто сколько внёс; открыть работника и внести за него), **«Напомнить тем, кто не внёс»** (не чаще раза в час; говорит, у кого нет Telegram), вечернее сообщение с кнопками «Напомнить» и «Внести по плану за всех», **мгновенное оповещение об отклонении** («Иванов: сделано 3 из 5, причина — нет материала») — и из бота, и из веб-версии;
— **«⚠ Проблема»** (сборщик): тип (нет материала, поломка, брак, другое) + текст и/или **фото** — бригадиру приходит сразу, фото пересылается; кнопка «👍 Принял» сообщает работнику. Если бригадир не подключён к боту, работник получает честное сообщение; факт обращения пишется в журнал;
— **«🤒 Не выйду»** (сборщик) и **«🤒 Отсутствие»** (бригадир, только свой участок): период и причина → создаётся отсутствие, работник/бригадир оповещаются, кнопка **«🔄 Перепланировать участок»** выполняет перепланирование прямо из бота;
— **уведомления работнику об изменении плана** (правка в веб-версии или перепланирование): на сегодня и завтра, «＋ добавлено, ✎ изменено, − убрано»; одинаковое состояние за день не повторяется;
— **«📅 Завтра»** — план на завтра (если выходной — ближайший день с заданиями);
— **«⚙ Настройки»**: у каждого своё время утреннего и вечернего сообщений (шаг 30 минут), включение/выключение, «Оповещения» (отклонения на участке / изменения в моём плане). О проблемах и отсутствии бригадир получает сообщения всегда. Миграция `0010` (`telegram_links.settings`).
Не сделано (сознательно): отправка файлов не хранится — фото только пересылается бригадиру; ввод из групповых чатов по-прежнему игнорируется.

**Этап 11 — сделано (мини-приложение Telegram).** Веб-страница внутри Telegram для сборщика и бригадира: крупные кнопки вместо команд.
— **Как открывается:** синяя кнопка «Приложение» рядом с полем ввода (ставится при привязке и по `/start`) и кнопка «📱 Открыть приложение» под приветствием и под каждым утренним/вечерним уведомлением. Нужен **HTTPS-адрес сервиса в `PLAN24_BASE_URL`** (Telegram не открывает `http`); при `http` кнопок нет, бот работает как раньше. Выключить — `PLAN24_TGAPP=off`. Страница: `/tg/`, API: `/api/v1/tgapp/*`;
— **вход без пароля и безопасность:** Telegram присылает приложению подписанные данные запуска; сервер проверяет подпись (HMAC-SHA256, ключ — токен бота), свежесть (`PLAN24_TGAPP_MAX_AGE`, по умолчанию сутки) и находит привязку чата — ту же, что у бота. Дальше токен сессии на 8 часов (хранится только в памяти страницы). Привязка проверяется при **каждом** запросе: отвязали чат или закрыли доступ — приложение перестаёт работать сразу. Неудачные входы ограничены по IP. Права те же, что у бота: сборщик — только своё и только сегодня, бригадир — только свой участок; токен приложения не подходит к веб-API и наоборот. Данные выводятся только как текст (нет `innerHTML`), внешних скриптов нет (`script-src 'self'`); страница `/tg/` — единственная, которую разрешено встраивать, и только в окна Telegram;
— **сборщик:** карточки заданий с «−/+», «+5», «+10», «Всё (план)», «0 — не делал», ручным вводом («3,5» понимается), прогресс дня, «↩ Отменить» после записи, вопрос о причине при факте ниже плана (бригадир получает оповещение), «Закрыть день по плану», вкладки «Завтра», «Проблема» (тип и текст; фото — в чате с ботом), «Не выйду»;
— **бригадир:** «Участок» (кто сколько внёс → открыть работника, внести за него, закрыть день за одного или за всех, напомнить, перепланировать), «Подтвердить» (очередь с бейджем), «Отсутствие» (с перепланированием), «Завтра»;
— действия бота и приложения — **один код** (`telegram/core.py`), поэтому поведение и права совпадают.

**Этап 12 — сделано (другая работа, полный доступ бригадира, назначение таблицей).**
— **Факт по любой работе** (если работника переключили): сборщик в мини-приложении и в боте («➕ Другая работа») выбирает **проект → заказ и изделие → операцию** из всех заказов в работе и вносит количество; операций можно добавить сколько нужно подряд (окно остаётся открытым, проект и заказ запоминаются). Запись идёт теми же правилами, что обычный ввод (сборщик — только за себя и за сегодня), в день она видна карточкой «вне плана» и редактируется как обычная. **Работа вне перечня операций** — описание и часы («Уборка», «Помощь на другом участке», можно привязать к заказу): добавляется, правится «＋/− 0,5 ч», удаляется; видна и в веб-версии. Бригадир делает то же за работников своего участка (мини-приложение, «Участок → работник → ➕ Другая работа»). В боте этот сценарий — для сборщика;
— **бригадир — полный доступ к работникам своего участка:** создание, правка (в том числе производительность, квалификация, статус), удаление, отпуска, привязка Telegram и **допуски к заказам** («Допуски»: показываются позиции, у которых есть операции его участка; допуски к остальным позициям, выданные руководителем, он не видит и не стирает). Перевести работника на другой участок по-прежнему может только руководитель проекта или администратор;
— **«Выполнение → Назначение»:** весь заказ в одной таблице — строки это операции заказа (норма, нужно, сделано, в плане, не назначено, участки), столбцы — 7 дней (выходные помечены, стрелки по неделям), в ячейках — работники. Выбрал работника — **подтягивается норма** (норма операции × производительность работника × коэффициент эффективности, но не больше невыполненного остатка по заказу и не больше свободной части дня), **день работника закрепляется автоматически**: перепланирование назначенное не изменит. Количество правится в ячейке; «×» снимает назначение (если у работника в этот день больше ничего нет, закрепление снимается). Предупреждения: перегрузка дня, отпуск/отсутствие, квалификация ниже требуемой (⚠), нерабочий день, объём сверх потребности. Работник получает сообщение в Telegram об изменении плана. Бригадир видит только операции и работников своего участка. API: `GET /plan-grid/orders`, `GET /plan-grid`, `POST /plan-grid/assign`, `DELETE /plan-grid/assign/{id}`.
