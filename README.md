# Plan 24 — сервис планирования производства (Модуль 1)

Компании регистрируются, заводят изделия, операции, исполнителей и заказы прямо в сервисе, вносят факт и получают
план по дням на каждого сборщика. Excel в основном сценарии не используется.

## Запуск
```bash
cd backend && pip install -r requirements.txt
python3 -m uvicorn plan24.app:app --port 8000        # интерфейс http://localhost:8000, документация API /api/docs
```
Локально: `PLAN24_ENV=dev python3 -m uvicorn plan24.app:app` (по умолчанию режим `prod`: нужен `PLAN24_SECRET`, отладочных возможностей нет).

| Переменная | Назначение |
|---|---|
| `PLAN24_ENV` | `prod` (по умолчанию) или `dev` |
| `PLAN24_SECRET` | подпись токенов; **обязателен** в prod (в dev создаётся сам) |
| `PLAN24_DB_URL` | БД приложения: `postgresql+psycopg://plan24_app:…@host/plan24` (боевой режим) или SQLite (по умолчанию, разработка) |
| `PLAN24_DB_MIGRATE_URL` | подключение **владельца схемы** для миграций (`alembic upgrade head`) |
| `PLAN24_DB_POOL`, `PLAN24_DB_OVERFLOW` | размер пула соединений |
| `PLAN24_DATA` | каталог данных SQLite |
| `PLAN24_BASE_URL` | публичный адрес сервиса для ссылок в письмах (`https://plan.example.com`) |
| `PLAN24_SMTP_HOST`, `_PORT`, `_USER`, `_PASSWORD`, `_SECURITY` (`starttls`/`ssl`/`none`), `PLAN24_MAIL_FROM` | отправка писем; без `PLAN24_SMTP_HOST` письма пишутся в файлы `data/outbox` (только разработка) |
| `PLAN24_TG_TOKEN`, `PLAN24_TG_SECRET`, `PLAN24_TG_BOT_USERNAME` | Telegram-бот (токен от @BotFather, случайный секрет вебхука, имя бота) |
| `PLAN24_TG_API_BASE`, `PLAN24_TG_PROXY` | адрес API Telegram (релей) и прокси — если `api.telegram.org` недоступен с вашего сервера |
| `PLAN24_TG_MODE` | режим бота в App Platform: `off` (по умолчанию) / `poll` / `webhook` |
| `PLAN24_DOCS=1` | опубликовать описание API (`/api/docs`) в prod; по умолчанию в prod скрыто |
| `PLAN24_TG_MORNING_AT`, `PLAN24_TG_EVENING_AT` | время утренних заданий и вечернего напоминания, по часовому поясу организации (07:30 / 17:30) |
| `PLAN24_TODAY` | только dev: зафиксировать «сегодня» |

### Подключение Telegram-бота
1. Создайте бота у @BotFather, задайте `PLAN24_TG_TOKEN`, `PLAN24_TG_SECRET` (длинная случайная строка), `PLAN24_TG_BOT_USERNAME`.
2. Сервис должен быть доступен по HTTPS: `python -m plan24.telegram setup-webhook https://plan.example.com`
   (без публичного адреса: `python -m plan24.telegram poll` — бот сам опрашивает Telegram).
3. Напоминания: `python -m plan24.telegram scheduler` (отдельный процесс) или `notify` по cron каждые 5–10 минут.
4. В «Данные → Исполнители» (или «Пользователи» для бригадира) нажмите «Telegram → Выдать код» и передайте код человеку.

## PostgreSQL (боевой режим)
Подробно — `docs/OPERATIONS.md`. Кратко: `deploy/postgres/init-roles.sql` → `alembic upgrade head` (владелец) → приложение под ролью `plan24_app`.
Защита на уровне строк (RLS) — вторая линия обороны: даже при забытом в коде фильтре по организации база не отдаёт чужие строки.
Прогон всего набора на PostgreSQL: `PLAN24_TEST_PG_SUPER_URL=postgresql+psycopg://postgres:…@localhost/postgres python3 -m pytest tests -q`
(создаёт БД `plan24_test`, применяет миграции, тесты идут под ролью без обхода RLS). Готовая сборка — `deploy/docker-compose.yml` (**не проверялась: нет Docker**).

**Timeweb Cloud:** два варианта — через **App Platform** (`deploy/timeweb/APPS.md`, корневой `docker-compose.yml`) или на своём облачном сервере (`deploy/timeweb/README.md`); проверочные скрипты и compose под управляемый PostgreSQL.

## Что сделано
- Организации, регистрация (согласие на обработку ПД), вход, refresh-токены с ротацией и обнаружением кражи, лимит попыток входа.
- Строгая изоляция организаций: фильтр по организации везде, проверка ссылок между сущностями, 404 вместо 403 на чужие записи.
- Данные: проекты, изделия + маршруты с версиями, операции (норма, квалификация, порядок/параллельность, блокировка с датой снятия),
  позиции заказов, исполнители, участки, отпуска, допуски к позициям, праздники, причины отклонений.
- Планировщик (`plan24/planner`, чистый Python): перенос Code_v3.5.gs, паритет с оригиналом проверяется эмулятором скрипта.
- План: снапшоты, один активный, откат, флаг «данные изменились после расчёта», заморозка ближайших дней, сравнение вариантов жёсткости.
- Факт: итог дня по исполнителю (повторный ввод заменяет), идемпотентность, подтверждение бригадиром, причины отклонений.
- Перепланирование участка: исполнители других участков и их назначенная работа остаются как есть.
- Письма: подтверждение e-mail, сброс пароля, приглашение сотрудника (SMTP; проверено на реальном SMTP-сервере).
- Telegram-бот: привязка по одноразовому коду (без пароля), задания дня, ввод факта кнопкой «всё» или числом с подтверждением, причины отклонений, «отменить последнее», очередь подтверждений бригадира, утренние задания и вечерние напоминания.
- Отчёты: план на день с фактом, статусы заказов, тепловая карта загрузки, обзор. Журнал изменений. Печать плана на день.

## Доработки (по списку «Доработки.txt»)
**Этап 1 — сделано:** вкладка «Дашборд» (бывший «Обзор»); новое меню «Каталог изделий», «Проекты и Заказы», «Организация» (участки, работники, календарь, пользователи, журнал, причины отклонений); настройки планировщика — кнопка в «Организация → Участки»;
перепланирование только по участкам (исключение — первый расчёт, когда плана ещё нет: он строится сразу по всем участкам); роль «Технолог» (создаёт и редактирует каталог изделий); «Заказчик» и выбор версии изделия в заказе.
**Этап 2 — сделано:** «Каталог изделий»: у версии маршрута есть название (задаётся при создании, переименовывается и у версии, уже стоящей в заказах), таблица изделий показывает текущую версию, число версий и операций; операции показывают норму, требуемую квалификацию и количество на изделие; название операции можно менять и в используемой версии (норму, порядок, квалификацию — только в новой версии).
Уровни квалификации настраиваются в «Организация → Об организации» (от 1 до 10, с названиями); у работника и у операции квалификация выбирается из этого списка; уровень, который кто-то использует, убрать нельзя. Миграция `0004`.
**Этап 3 — сделано:** в «Проекты и Заказы → Заказы» у каждой позиции есть кнопка «По участкам» и колонка «Операции по участкам»: для каждой операции отмечаются участки (можно несколько). Операция выполняется только работниками своих участков; **операция без участка — ошибка** (`NOT_DISTRIBUTED`): она не попадает в план, следующие за ней операции тоже не планируются, на дашборде красная ошибка с кнопкой «Распределить». Бригадир видит только операции своего участка и только позиции, где они есть. Миграция `0005` (таблица `order_line_operations` с RLS).
**Этап 4 — сделано («План на день»):**
— правка плана вручную: «+ Задание» (можно несколько операций на день), «Изменить» (работник, день, заказ, операция, количество; заказ выбирается с фильтрами по проекту и изделию), «Убрать»;
— **закрепление:** любая правка закрепляет день работника — перепланирование участка его не меняет (в том числе удаление задания); кнопка «Снять закрепление» возвращает день планировщику; откат плана восстанавливает закрепления из возвращаемого плана;
— «+ Работа вне перечня»: работа по заказу (но без операции в маршруте) или не по заказу (уборка, наладка), учёт в часах, свой факт;
— «+ Работник»: временный работник сохраняется в списке работников, но автопланировщик заказов ему не даёт (поле «Участвует в автопланировании» в «Организация → Работники»);
— факт: понятная форма («Сделано», «Всё: N», «Не делали», «Записать выполнение»), причина или комментарий запрашиваются **только** при отклонении — факт меньше плана или выполнено больше, чем нужно по заказу; кнопка «Всё по плану» на работника.
Миграция `0006` (закрепления дней, работы вне перечня, флаги работника).
**Дальше:** 5 — статус заказов, 6 — наполнение дашборда.
Работник без участка не попадает в перепланирование по участкам — у каждого работника должен быть участок.

## Что пока нет (этапы C–E ТЗ)
Отчёт по проекту, узкие места, планирование ресурсов, рекомендации «что нужно, чтобы успеть», ввод факта через Telegram,
уведомления о риске опоздания и перегрузке (FR-37), тарифы и оплата, асинхронные задачи (перепланирование синхронное),
лендинг, юридические документы, двухфакторная аутентификация.

## Известные ограничения
- Docker-образ и compose-файл написаны, но не собирались и не запускались (в среде разработки нет Docker); проверены по частям: команды контейнера, инициализация ролей, миграции, резервное копирование и восстановление. PostgreSQL проверялся только версии 16.
- Refresh-токен хранится в `localStorage` (переживает перезагрузку, уязвим при XSS; CSP запрещает внешние и inline-скрипты, весь вывод экранируется).
- Telegram-бот проверен на поддельном клиенте и на запросах к Bot API через mock-транспорт, **но не против настоящего Telegram**; SMTP проверен без шифрования, режимы STARTTLS/SSL — нет.
- Интерфейс проверялся в jsdom, не в реальных браузерах, мобильную вёрстку глазами никто не смотрел.
- Расхождения ТЗ и скрипта, дефекты оригинала и принятые решения — `docs/DEVIATIONS.md`.
