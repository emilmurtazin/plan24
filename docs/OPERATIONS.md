# Эксплуатация Plan 24 на PostgreSQL

## Роли базы данных (принцип наименьших привилегий)
| Роль | Для чего | Права |
|---|---|---|
| `plan24_owner` | владелец схемы; **только миграции** | создаёт/меняет таблицы; RLS на неё не действует |
| `plan24_app` | приложение (веб, планировщик напоминаний) | DML на таблицы; **не владелец, не суперпользователь, без BYPASSRLS** → подчиняется RLS; в `audit_log` только SELECT/INSERT; организации не удаляет |
| `plan24_admin` | аварийный доступ администратора БД, обход RLS | в приложении и скриптах приложения не используется; доступ выдавать персонально и фиксировать |

Приложение **отказывается стартовать**, если подключено ролью-суперпользователем/владельцем/BYPASSRLS или если схема не на последней ревизии
(отключение проверки роли только для разработки: `PLAN24_ALLOW_PRIVILEGED_DB=1`).

## Первичное развёртывание
1. `deploy/postgres/init-roles.sql` — создать роли и БД (один раз, суперпользователем). В Docker это делает `docker-init.sh`.
2. Миграции: `PLAN24_DB_MIGRATE_URL=postgresql+psycopg://plan24_owner:...@host/plan24 alembic -c backend/alembic.ini upgrade head`.
3. Приложение: `PLAN24_ENV=prod PLAN24_SECRET=... PLAN24_DB_URL=postgresql+psycopg://plan24_app:...@host/plan24 uvicorn plan24.app:app`.
4. Проверка: `GET /api/v1/health/ready` → `{"status":"ready","database":"postgresql"}` (503, если БД недоступна или схема устарела).
Готовая сборка: `deploy/docker-compose.yml` (db → migrate → web + scheduler), секреты — `deploy/.env.example`. TLS — обратный прокси (`deploy/Caddyfile`).

## Обновление версии
1. **Резервная копия** (`deploy/postgres/backup.sh`).
2. **Миграции до запуска новой версии** (`docker compose run --rm migrate`): новая версия кода при старте проверяет ревизию и не запустится на старой схеме.
3. Перезапуск `web`. Миграции пишите совместимыми со старой версией (добавлять — можно; удалять/переименовывать — в два релиза), чтобы обновление шло без простоя.
4. Откат: `alembic downgrade <ревизия>` возможен только для обратимых миграций; после миграций с потерей данных откат — **восстановление из копии**.

## Как устроена защита на уровне строк
* Токен доступа содержит организацию (`tid`). Сразу после проверки токена приложение выставляет в транзакции `app.tenant_id`
  (`set_config(..., is_local=true)`: действует до конца транзакции, в пул не «утекает»). Без неё политики не пропускают **ни одной строки**.
* До входа организация неизвестна (вход, обновление токена, подтверждение e-mail, сброс пароля, привязка Telegram). Для этого есть режим
  `app.auth_scope=on`: **только чтение** `users`, токенов и привязок/кодов Telegram. Сразу после нахождения учётной записи приложение
  переключается в контекст её организации, и вся запись идёт уже в нём.
* Новая организация получает id заранее (`nextval`), чтобы политика пропустила её создание; создать организацию с чужим id нельзя.
* **Добавляете таблицу?** В миграции: `ENABLE ROW LEVEL SECURITY` + политика `tenant_isolation` (по образцу 0002) и колонка `tenant_id`.
  Тест `test_every_table_declares_rls_posture` падает, если таблица осталась без защиты и не внесена в список исключений осознанно.
* **Данные миграций** выполняет владелец схемы — RLS на него не действует; пишите их с явным `tenant_id`.

## Резервные копии и восстановление
* Копия: `PGUSER=plan24_admin PGPASSWORD=… deploy/postgres/backup.sh /backups` (формат custom, вместе с политиками и правами). Запускать по расписанию, хранить вне сервера БД.
* **Проверяйте восстановление**, а не только наличие файла: `deploy/postgres/restore-check.sh файл.dump` разворачивает копию во временную БД и печатает число таблиц/политик/ревизию.
  Проверено: после восстановления данные, политики, права роли приложения (в т. ч. запрет UPDATE/DELETE в `audit_log`) совпадают с исходной БД.
* Восстановление в боевую БД: остановить `web`/`scheduler`, `pg_restore --clean --if-exists --no-owner --role=plan24_owner -d plan24 файл.dump`, `alembic upgrade head`, запустить сервисы.

## Масштабирование
* Воркеров × (`PLAN24_DB_POOL` + `PLAN24_DB_OVERFLOW`) не должно превышать `max_connections` PostgreSQL (с запасом на миграции и администратора).
* Планировщик напоминаний (`scheduler`) достаточно в одном экземпляре; даже при двух дублей не будет (уникальный журнал отправок).
* Перепланирование одной организации выполняется по одному (advisory-блокировка), разных организаций — параллельно. Блокировку держит отдельное соединение,
  поэтому **PgBouncer в режиме transaction pooling для веб-процессов не подходит** (нужен session pooling или прямое подключение). Всё остальное
  (`set_config(..., true)`) с transaction pooling совместимо.
* Ограничение частоты входа общее для всех процессов (таблица `rate_events`, только хеши).

## Диагностика
| Сообщение | Причина |
|---|---|
| «Схема БД на ревизии …, нужна …» | не применены миграции → `alembic upgrade head` |
| «Приложение подключено ролью с правами обхода RLS» | в `PLAN24_DB_URL` указана не `plan24_app` |
| «Роль приложения … не создана» при миграции | не выполнен `init-roles.sql` |
| Запросы возвращают пусто, хотя данные в БД есть | не выставлен `app.tenant_id` (новый код, обращающийся к БД до проверки токена) |
| `permission denied for table …` | таблица создана не миграцией владельца или права не выданы |

## Панель суперадмина

Адрес `/admin`. Панели нет, пока на сервере не заданы `PLAN24_SUPERADMIN_EMAIL` и `PLAN24_SUPERADMIN_PASSWORD_HASH` (тогда `/admin` и `/api/v1/superadmin/*` отвечают 404).

1. Хеш пароля (пароль не короче 12 символов, вводится скрыто и нигде не сохраняется). Проще всего на своём компьютере, где есть Python 3.12:
   ```
   cd backend
   python -m venv .venv && source .venv/bin/activate        # Windows: .venv\Scripts\activate
   pip install -r requirements-prod.txt
   python -m plan24.superadmin_tool
   ```
   На сервере с Docker: `docker compose run --rm --no-deps --entrypoint python web -m plan24.superadmin_tool` (`--entrypoint python` обязателен: скрипт запуска контейнера принимает только свои команды).
2. Задайте e-mail и хеш переменными окружения сервиса `web`. В `.env`/compose знак `$` в хеше удваивается (`$$`) — утилита печатает обе формы.
3. Перезапустите `web`. Миграция `0013` (колонки блокировки и политики RLS режима платформы) выполняется сервисом `migrate` при деплое.

Возможности: сводка и список организаций (пользователи, работники, заказы, Telegram, последняя активность), блокировка и разблокировка организации с причиной, отключение и включение пользователей, письмо со ссылкой для смены пароля (пароль суперадмин не видит и не задаёт), вход под организацией для поддержки.

Безопасность:
* отдельный токен суперадмина (`typ=platform`, 60 минут, без обновления); им нельзя пользоваться в API организаций, токеном организации — в панели; вход ограничен по частоте (5 неудач за 15 минут с одного адреса, 30 — на всю платформу);
* блокировка действует сразу: токены организации перестают приниматься, обновление сессий закрыто, бот Telegram отвечает «Доступ приостановлен», рассылки не отправляются;
* вход под организацией: токен на 30 минут без обновления, в нём нельзя менять пароль и e-mail, «Выйти» не закрывает настоящие сессии владельца, каждое действие помечается в журнале организации (`via_support`), сам вход и все действия суперадмина записываются в журнал организации (`entity=tenant`, `action=platform_*`);
* в базе режим платформы — отдельные политики RLS (`app.platform_scope`): чтение организаций, пользователей и сводных таблиц (`tenants`, `users`, `workers`, `order_lines`, `plans`, `audit_log`, `telegram_links`), запись только блокировки организации, статуса пользователя, токенов и добавления записи в журнал. Содержимое данных организаций (изделия, факты, планы по строкам) режиму платформы недоступно.
