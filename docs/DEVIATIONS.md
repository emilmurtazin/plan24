## Мутационная проверка набора паритета

Преднамеренные поломки правил (округление, лимит людей на операцию, порог загрузки, заморозка, готовность групп, граница жёсткости) ловятся тестами. Единственный неуловимый мутант — `>` вместо `>=` в `prio_share_day` — эквивалентен из-за допуска 1e-9.

## Исправленные дефекты при разработке (регрессии покрыты тестами)

- Поздний коммит: по умолчанию FastAPI завершает зависимости с `yield` **после** отправки ответа, клиент мог прочитать ещё не сохранённое (после регистрации следующий запрос получал 401). Коммит теперь до ответа (`scope="function"`). Тест: `test_commit_happens_before_response_is_sent`.
- SQLite: чтение без общей транзакции давало рассогласованные данные внутри одного расчёта. Включены явные транзакции и WAL; запись — `BEGIN IMMEDIATE`. Тесты: `test_sqlite_reader_sees_one_consistent_snapshot`, `test_concurrent_writers_and_readers_never_get_server_errors`.
- Допуск «никому не разрешено» превращался в «разрешено всем» (в скрипте — предупреждение). Набор паритета `edge_order_nobody_allowed`.
- Интерфейс: запоздавший ответ прежнего экрана перерисовывал другую вкладку. Регрессия в `tests_ui/smoke.js`.

| D-53 | **Снимки плана по дням** (`day_plan_snapshots`): строки активного плана на сегодня и будущее перезаписываются при каждом перепланировании, откате, ручной правке, раз в сутки при первом открытии дашборда и в планировщике рассылок (по часовому поясу организации); прошедшие дни не трогаются. Список организаций для суточной задачи берётся по пользователям (в режиме `auth_scope` читаются только они). Планировщик рассылок завершается, если Telegram не настроен, — поэтому есть ленивое сохранение при открытии дашборда | Данных о том, что планировалось на прошедший день, раньше нигде не было |
| D-54 | **Недовыполнение** = Σ max(0, план задания − внесённый факт этого же задания) по прошедшим дням (сегодня не входит); задание без факта считается невыполненным; перевыполнение не гасит недовыполнение других заданий. Показывается по неделям и участкам (участок — на момент снимка), % от запланированного. История копится только с выкатки | Простое, проверяемое определение; «нет факта = не сделано» делает дыры во внесении факта видимыми |
| D-55 | **Загрузка на 3 месяца** — средняя загрузка работников участка по неделям из матрицы загрузки плана; недели за горизонтом планирования не показываются (план не строится на 3 месяца вперёд, горизонт задаётся сроками заказов). Работы вне перечня в загрузку не входят (D-44) | Не выдумываем данные, которых планировщик не считал |
| D-56 | **Потребность в ресурсах** считается по заказам в риске (до 25, ближайшие сроки): для каждой операции берётся структурированная оценка из статуса заказа (D-50); по участку показывается максимум по его операциям (а не сумма: люди работают последовательно), плюс нехватка квалификации и недели загрузки выше 100% | Один работник может закрыть несколько операций; сумма завысила бы потребность |
| D-57 | «Повторяющиеся причины» — по внесённому факту за 90 дней; повторяющейся считается причина, указанная два раза и больше; факты только с комментарием собираются в «Без причины (комментарий)» | Единственный источник причин — факт |

## PostgreSQL, RLS и миграции

| № | Решение | Почему |
|---|---------|--------|
| D-18 | RLS включена, но **не `FORCE`**; вместо этого приложение не стартует под владельцем/суперпользователем/BYPASSRLS | `FORCE` подчинил бы RLS и миграции владельца (данные миграций пришлось бы писать «через политики»). Охрана при старте даёт то же для приложения, не мешая миграциям. |
| D-19 | Режим `auth_scope` — только чтение, и только в точках входа без авторизации | До входа организация неизвестна. Альтернативы (отдельная роль с BYPASSRLS, SECURITY DEFINER-функции) шире по привилегиям. Запись в этом режиме запрещена политиками и проверена тестом. |
| D-20 | В `plan_items` и `telegram_state` добавлен `tenant_id` | Прямая политика и быстрые выборки вместо подзапросов; у `refresh_tokens`/`email_tokens` организации нет — они изолированы через пользователя. |
| D-21 | PostgreSQL ведётся только Alembic (приложение не делает `create_all`); SQLite остаётся для разработки/тестов через `create_all`, миграции проверены и на нём | Исключает «схема в проде не такая, как в коде»; тест сравнивает схему после миграций с моделями (расхождений 0; детектор проверен на искусственной правке). |
| D-22 | Ограничитель частоты: PostgreSQL — таблица `rate_events` (общая для процессов), SQLite — память | В памяти лимит при N воркерах был бы N-кратным. На SQLite отдельное соединение конфликтует с блокировкой записи запроса. |
| D-23 | Перепланирование: advisory-блокировка на организацию + `REPEATABLE READ`, фиксация до снятия блокировки | Параллельные перепланирования не дают двух активных планов и читают единый снимок. |
| D-24 | Журнал аудита неизменяем для роли приложения (нет UPDATE/DELETE/TRUNCATE), организации приложением не удаляются | Защита следов от ошибок и компрометации приложения. Удаление организации (152-ФЗ, по запросу) — отдельная административная процедура. |

Найдено при переходе на PostgreSQL (на SQLite скрывалось сериализацией записей): гонка «вставить или заменить» при одновременном вводе одного итога факта давала 500;
то же — для ключа идемпотентности и e-mail пользователя. Исправлено, регрессии в `test_rls.py`.

## Доработки: партии на операциях, настройки по участкам, без «жёсткости по уровням»

| № | Что | Как реализовано |
|---|---|---|
| D-40 | **Партия на операции.** Следующая по порядку операция может стартовать, когда предыдущая выполнена на N % изделий заказа. | Поле `operations.start_after_pct` (1–100; пусто или 100 — как раньше, только после полного окончания предыдущей; для операций первого порядка не действует). Если задано, операция стартует в день, когда предыдущая (все операции предыдущего порядка) выполнила N % изделий, и дальше берёт изделия по мере готовности: накопленный объём операции на любой день не больше накопленного объёма предыдущей. Считается по плану, закреплённым строкам и внесённому факту. Если за горизонт порог не достигнут, операция не планируется. Поле можно менять и у маршрута, уже стоящего в заказах (состав работ не меняется). Паритет со скриптом сохранён: без `start_after_pct` расчёт побитово прежний. |
| D-41 | **Настройки планирования по участкам.** | У участка свои: эффективность, макс. исполнителей на операцию, порог загрузки «сегодня», мин. доля старта (`work_centers.*`). Пусто — действует общее значение из «Организация → Планирование». Значения применяются к работникам участка (`Worker.efficiency` и др. в планировщике); предел исполнителей действует отдельно для каждого участка, у которого он задан. Общими остались: жёсткость приоритета, заморозка, рабочие дни недели, длительность смены, подтверждение факта, флаг D-04. |
| D-42 | **«Жёсткость по уровням приоритета» удалена** (`strictness_by_level`: поле настроек, параметр перепланирования, колонка БД — миграция 0012). | Остаётся общая «Жёсткость приоритета». Набор паритета `edge_strictness_levels` теперь без `byLevel`. |
| D-43 | **Предшественники операций.** Вместо ожидания всего предыдущего порядка операция может зависеть только от выбранных операций маршрута. | Поле `operations.predecessors` (JSON, миграция 0014): `NULL` — как в скрипте (ждёт весь предыдущий порядок), список имён — ждёт только перечисленные (старт не раньше дня окончания последней из них, изделий не больше, чем они выпустили), пустой список — стартует сразу. Предшественник — операция того же маршрута с **меньшим** порядком (поэтому циклов нет; проверяется API). Переименование операции обновляет ссылки, удаление убирает её из списков (опустевший список возвращается к «по порядку»). Поле можно менять и в маршруте, уже стоящем в заказах. С партиями (D-40) сочетается: порог считается по выпуску предшественников. Для операций без `predecessors` расчёт прежний, паритет со скриптом сохранён. |
